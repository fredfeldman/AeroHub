# AeroHub User Guide

## 1. About AeroHub

AeroHub is a local aviation SDR and decoded-data operator console. It brings aviation messages, aircraft tracks, Remote ID drone reports, radiosonde telemetry, source health, imports, WEFAX images, and storage operations into one web interface.

The backend owns data ingestion, validation, normalization, storage, and live events. The web console displays that information and provides operator controls. AeroHub can use sample fixtures and decoded records without an SDR connected. A visible track, running source state, or successful replay does not by itself prove that live RF was received or decoded.

This guide describes the current implementation. Some panels are demonstration or simulator workflows; they are labelled below.

## 2. Requirements

### Packaged Windows installation

- Windows x64.
- The per-user AeroHub installer generated by the repository packaging process.
- No separate .NET or Node.js installation is required by the self-contained packaged build.

### Running from source

- .NET 8 SDK or later compatible with the solution.
- Node.js with npm.
- A PowerShell terminal at the repository root.

## 3. Start AeroHub

### Packaged application

1. Install AeroHub using `AeroHub-Setup.exe`.
2. Start AeroHub from the Start Menu shortcut (or the optional desktop shortcut).
3. Open `http://localhost:5157` if the browser does not open automatically.
4. Confirm the backend indicator reports online and the live-updates indicator shows connected.

The installer is per-user. The app host serves the built React interface and the API from the local application process.

### Local development

From the repository root, start the backend:

```powershell
dotnet run --project .\src\backend\AeroHub.Api\AeroHub.Api.csproj --urls http://localhost:5157
```

In a second terminal, start the frontend development server:

```powershell
Set-Location .\src\frontend\AeroHub.Web
npm install
npm run dev -- --host 127.0.0.1
```

Open the local URL printed by Vite. The development frontend proxies `/api` and `/hubs` to the backend on port 5157. Keep the backend running while using the development UI.

### Build or test from source

From the repository root:

```powershell
dotnet restore .\src\backend\AeroHub.slnx
dotnet build .\src\backend\AeroHub.slnx
dotnet test .\src\backend\AeroHub.slnx
```

From `src/frontend/AeroHub.Web`:

```powershell
npm run typecheck
npm run lint
npm run build
```

## 4. Read the Console Status

The top-right status area contains two separate indicators:

- **Backend:** whether the API host responded to its health check. An offline indicator means data requests and controls may fail.
- **Live updates:** SignalR connection state. When connected, messages, tracks, diagnostics, source changes, and other events update without a page refresh. The client attempts automatic reconnection and requests fresh snapshots after reconnecting.

Panels show a state, last action result, counters, or diagnostics where applicable. Check source/import provenance and diagnostics before treating an item as live data. The activity log in the left sidebar summarizes recent operator actions.

## 5. Console Navigation

Use the left sidebar to jump to:

- **Live RF:** spectrum, waterfall, source adapters, data feeders, and replay controls.
- **Messages:** recent normalized aviation messages and confidence/warning filters.
- **Map:** positioned tracks, map filters, history playback, and export.
- **Aircraft:** track counts, storage health, dump1090 network connection, and the aircraft table.
- **Decoders:** selected message detail and decoder-related status.
- **Imports:** sample imports, import state, quarantines, and diagnostics.
- **WEFAX:** image replay, polarity/slant controls, and sync status.
- **Settings:** saved decoder, track, WEFAX, and dump1090 preferences.

The Commercial Drone Tracking and RadioSonde Telemetry panels appear below Imports in the main console.

## 6. Live RF and Source Adapters

### Synthetic spectrum and waterfall

Use **Replay 1x**, **Replay 5x**, or **Replay 20x** in Live RF to generate synthetic visualization data at the selected multiplier. The spectrum and waterfall are replay products, not a measurement of an attached receiver. Stream metrics report frame/row counts, queue depth, dropped frames, and related client health.

### Source adapters

The Source Adapters panel currently lists:

- `file-audio-iq`: a file/audio-style adapter surface.
- `rtl-tcp-local`: an rtl_tcp-style SDR adapter surface.

The current hardware-source manager is simulator-first. Its start action exercises source ownership, state, and metrics; it does not prove that a real audio device or RTL-SDR has delivered samples. The UI also offers diagnostic simulations such as buffer drop, reconnect, clipping, and failure. Use these controls to test status handling, not to diagnose actual hardware.

Review a source's state, owner, capability range, sample rate, bandwidth, queue, drops, reconnects, SNR, and last error. A source that reports online is not the same as a completed decoder producing validated messages.

### Data feeders

The Data Feeders panel lists configured FlightAware feeder entries and their protocol, mode, destination, frame/byte counters, connected clients, state, and diagnostics. Start or stop only a feeder that you have intentionally configured. The **test-frame** action sends a test frame through that feeder. Confirm the destination and network policy before enabling outbound transmission.

## 7. Review Aviation Messages

The Messages panel displays recent normalized messages. Use the Filter menu to show all messages, a confidence category (`Confirmed`, `Candidate`, `Observed`, or `Unknown`), or messages with warnings.

Select a message to populate Message Detail. Depending on the source and parser, details may include:

- ACARS label, sublabel/preamble, application category, and aircraft identifier.
- Datalink application type, direction, message reference, acknowledgement state, and category.
- SATCOM satellite/channel/bearer and reassembly state, when present.
- Original raw payload, provenance path, source app/format, transport, frequency, and parser warnings.

Use **Copy raw** on a message or **Copy raw payload** in Message Detail to place the preserved payload on the clipboard. Unknown or placeholder payloads may be retained without a full structured application parser; read warnings and confidence rather than assuming a complete decode.

**Replay ACARS Fixture** publishes the bundled ACARS fixture through the message pipeline. It is useful for checking the message table and parser behavior; it is not a live ACARS reception action.

## 8. Map and Aircraft Tracks

The map combines aircraft tracks, radiosonde positions, and nearby radio navigation aids. Its initial view is centered near Allen, Texas; the map view is saved in the browser. Pan and zoom to explore the map. The **Aircraft list** beside the map can be used to select a track; selecting a track opens its marker and details.

### Map controls

- **Show flight track for selected aircraft:** display the available recent path for the selected track.
- **Show range rings:** show distance rings at 50-mile intervals.
- **Show radio navaids:** toggle the available navigation-aid overlay.
- **Cluster markers when zoomed out:** combine nearby aircraft markers at low zoom levels.
- **Only show last hour of traffic:** hide tracks whose latest update is older than one hour.
- **Follow selected aircraft:** pan the map as the selected position changes.
- **Position only:** hide tracks without latitude/longitude.
- **Class filters:** include or exclude Military, Government, Commercial, Civilian, and Unknown classifications.
- **Alt min / Alt max:** filter tracks by the shared aircraft altitude field in feet.
- **Export (CSV) / Export (GeoJSON):** download the currently filtered map tracks. CSV includes track identity/type/class and position/motion fields; GeoJSON exports positioned tracks.

The shared altitude filter is in feet. Remote ID geodetic and height-above-ground values are shown separately in meters in the drone panel and are not substituted into this generic aircraft altitude filter.

Select a track to inspect its identifier, source, confidence, position, altitude/speed/heading when available, and update time. Aircraft positions are retained in a bounded position history for map trails and history playback. The aircraft store expires tracks after 15 minutes without a fresh update by default; the saved stale-track setting is shown in Settings. The one-hour map filter is a separate display filter.

## 9. ADS-B and dump1090/readsb

The Aircraft panel includes an optional network connection to an already-running dump1090/readsb-compatible JSON endpoint.

1. Enter the host or IP address reachable from the AeroHub computer.
2. Enter the JSON port, path, and poll interval. The defaults are port `8080`, `/data/aircraft.json`, and 5 seconds.
3. Select **Connect**. Watch the state, last-poll time, accepted/quarantined counts, and diagnostics.
4. Select **Disconnect** to stop polling.

Common JSON paths include `/data/aircraft.json` for stock dump1090-style endpoints and `/skyaware/data/aircraft.json` for some dump1090-fa installations. Use the path actually served by your receiver. AeroHub polls the configured HTTP endpoint; this does not start dump1090 itself.

The **Start ADS-B Import** control in Imports loads the included readsb-style sample fixture. It validates ICAO hex addresses, coordinates, and position age before creating tracks. A successful fixture import should be identified as imported sample data by its source/provenance.

## 10. Commercial Drone / Remote ID

The Commercial Drone Tracking panel separates individual decoded Remote ID messages from the latest merged drone track.

- Select **Import Remote ID Sample** to load the bundled demonstration fixture.
- Review active tracks and recent messages. Basic ID, Location/Vector, and other message types can arrive independently; a valid observation can exist without a position.
- The observation display can show UAS identity/type, operator ID, message family, coordinates, altitude references, speed/direction/vertical speed, accuracy, System area values, Self-ID, source-reported authentication, validation warnings, radio/channel/RSSI, receiver, and receive time when the input supplied those fields.
- Geodetic altitude, barometric altitude, and height above ground are separate values in meters. Do not interpret an absent altitude reference as a known datum.
- `UAS ID`, serial/session identity, operator ID, and observed radio MAC are distinct. An observed MAC is not used as the durable UAS identity.
- An operation is classified as commercial only when the input explicitly supplies that operation type. AeroHub does not infer commercial use from serial, operator ID, UA type, or aircraft presence.

Remote ID tracks also appear on the shared map when the message contains coordinates. The sample fixture is not a radio receiver. Live Remote ID tracking requires a separate receiver or service to provide decoded records in AeroHub's supported format. Recent Remote ID message observations are currently held in a bounded in-memory window of up to 1,000 entries and are lost when the backend restarts; they are not included in the persistent storage export.

For field definitions and validation behavior, see [docs/commercial-drone-tracking.md](docs/commercial-drone-tracking.md). The user-facing sample import ID is `local-remote-id-json`.

## 11. Radiosonde Telemetry

Select **Start RadioSonde Import** to load the bundled telemetry sample. The RadioSonde Telemetry panel shows available serial/type, altitude, ascent rate, temperature, humidity, pressure, frequency, frame number, RSSI, and burst state. Its import includes example rejected records so the import diagnostics can demonstrate validation and quarantine behavior.

The sample import does not tune an SDR or receive a radiosonde transmission. Live reception requires an implemented receiver/decoder input that supplies compatible decoded telemetry.

## 12. Imports and Diagnostics

Imports uses the same validated ingestion flow for bundled sample data. Current console actions are:

| Console action | Import ID | What it demonstrates |
|---|---|---|
| Start NDJSON Import | `local-acars-ndjson` | Imported ACARS payload normalization and quarantine diagnostics. |
| Start ADS-B Import | `local-adsb-readsb-json` | Readsb-style aircraft tracks and position validation. |
| Start SATCOM Import | `sample-satcom-json` | SATCOM-related decoded sample messages and metadata. |
| Start RadioSonde Import | `local-radiosonde-json` | Sample radiosonde telemetry. |
| Import dumphfdl | `sample-dumphfdl-json` | HFDL sample payloads; ACARS content can use the ACARS parser and other payloads may remain placeholders. |
| Import dumpvdl2 | `sample-dumpvdl2-json` | VDL2 sample payloads; ACARS content can use the ACARS parser and CPDLC may remain a placeholder. |
| Import Remote ID Sample | `local-remote-id-json` | Individual Remote ID observations plus positioned drone tracks. |

An import normally reports accepted records and quarantined records. The Imports list also shows source format, state, counters, and last error. Diagnostics identify malformed JSON, missing fields, oversized records, duplicate source event IDs, stale or invalid positions, unsupported record kinds, and out-of-order track updates depending on adapter. A quarantined record is not necessarily a failed import run; inspect individual diagnostics to understand what was rejected.

The external-decoder status panel is currently a process-supervision skeleton with simulated scenarios. Its start/crash/timeout/malformed-output/restart-limit controls exercise state and diagnostics; the app does not currently launch dumphfdl, dumpvdl2, or dump1090 as real external processes through those controls. Sample imports remain available independently.

## 13. WEFAX

WEFAX currently provides synthetic replay and controls to exercise its image and status workflow:

- **Replay WEFAX:** generates a complete synthetic image-line replay.
- **Replay Partial:** generates a partial replay that ends with degraded synchronization.
- **Invert:** changes the image polarity control.
- **Slant:** adjusts line slant correction within the control range.
- **Resync:** resets polarity and slant controls to their neutral values.

The panel displays the image canvas, sync state, IOC, line rate, received line count, and warnings. Replay data is synthetic and should not be treated as a received weather fax.

## 14. Settings

Settings are saved through **Save Settings** and persisted by the backend. Current controls include:

- **Stale Track Expiry:** track expiry value in minutes (bounded by the backend settings sanitizer).
- **Default IOC / Line Rate:** WEFAX replay/decoder defaults.
- **dump1090 Default Host:** saved host value for the network ADS-B source.
- **Auto-connect on backend startup:** automatically reconnect to the configured dump1090 endpoint when a host is configured.

WEFAX polarity/slant controls update their settings as they are changed. Dump1090 host, port, path, and poll interval can also be entered in the network ADS-B panel; connecting there saves the connection settings and enables auto-connect. The current settings file is under the app data directory at `data/store/settings.json`, with a backup file used for recovery. Packaged installs keep this data in the app's runtime data location, not in the source checkout.

## 15. Storage, Export, and Retention

The Aircraft panel includes **Refresh Storage**, **Export Snapshot**, and **Apply Retention**.

- **Refresh Storage** reloads counts and byte usage.
- **Export Snapshot** writes the current supported persistent records to an export folder and reports exported messages, tracks, and diagnostics.
- **Apply Retention** asks for confirmation because it permanently removes expired records. The current UI action uses the API defaults: messages older than 30 days, tracks older than 30 days, and diagnostics older than 14 days.

The persistent record store uses SQLite at `data/store/aerohub.db`. Settings are stored separately as JSON. Aircraft position history is bounded per aircraft. Remote ID observations are currently an in-memory-only feature and are not part of persistent record counts or snapshot exports. Review the export and retention result messages before relying on a data archive.

## 16. API and Live Updates

The local API uses `http://localhost:5157` for the packaged app and the documented development backend. Useful read endpoints include:

| Endpoint | Purpose |
|---|---|
| `GET /api/health` | Backend version, environment, and capability/status summary. |
| `GET /api/diagnostics/operator` | Operator health, queue, warnings, and storage usage summary. |
| `GET /api/messages/recent?limit=50` | Recent normalized messages. |
| `GET /api/imports` | Import source states and counters. |
| `GET /api/imports/diagnostics?limit=50` | Recent import diagnostics. |
| `GET /api/aircraft` | Current non-stale aircraft tracks. |
| `GET /api/aircraft/{id}/history?limit=300` | Position history for a track. URL-encode identifiers containing special characters. |
| `GET /api/remote-id/observations?limit=100` | Recent decoded Remote ID observations; in-memory window. |
| `GET /api/sondes` | Current radiosonde tracks. |
| `GET /api/navaids?maxDistanceMiles=200` | Navigation-aid catalog entries. |
| `GET /api/storage` | Storage counts and bytes used. |
| `GET /api/settings` | Saved decoder settings. |

The SignalR hub is `/hubs/aerohub`. It provides live message, aircraft, Remote ID observation, import, diagnostics, spectrum/waterfall, WEFAX, feeder, and source events, as well as snapshot methods used by the UI after connection or reconnect. Development Swagger is available when the backend runs in the Development environment.

The API and control surface are intended for local operator use. Do not expose the host or control endpoints to an untrusted network without adding appropriate authentication, authorization, and network protections. In particular, dump1090 connect accepts a host and path to poll, and feeder start can send traffic to configured targets.

## 17. Troubleshooting

### Backend shows offline

- Confirm the packaged AeroHub process is running, or start the backend development command.
- Open `http://localhost:5157/api/health` locally to check the API host.
- Check whether another process is using port 5157; if so, configure a different host URL consistently for the backend and frontend proxy.

### Backend is online but live updates are disconnected

- Refresh the page after confirming `/hubs/aerohub` is reachable.
- In development, make sure Vite's `/hubs` proxy points to the active backend URL.
- A SignalR reconnect requests fresh snapshots. If the issue persists, check the backend console output.

### Import button reports an error or no tracks appear

- Check the import source's state and last error in Imports.
- Review the diagnostics list for schema mismatch, stale position, invalid coordinates, duplicate records, or out-of-order updates.
- A record can be accepted as a Remote ID observation but not become a map track if it has no position.
- Fixture imports show demonstration data; they do not confirm receiver connectivity.

### dump1090 stays degraded or has no tracks

- Confirm host, port, and JSON path from another browser or machine on the same network.
- Verify the AeroHub computer can reach that endpoint and that a firewall permits the connection.
- Use the endpoint actually served by your dump1090/readsb installation; inspect poll errors and rejected-record diagnostics.

### No live RF data appears

- The sample source adapter manager is simulator-first. Source state and simulated metrics alone do not prove that RF samples were received.
- Confirm the chosen hardware/decoder adapter is an implemented live input path. See [docs/hardware-source-adapters.md](docs/hardware-source-adapters.md).
- Use the bundled fixtures to validate the UI separately from hardware.

### Data disappeared after restart

- Check whether it was a persisted message/track or a bounded runtime cache.
- Remote ID observations are currently in memory and are cleared when the backend restarts.
- Exports contain supported persisted messages, tracks, and diagnostics; they do not archive every transient runtime product.

## 18. Data Interpretation and Privacy

- Source provenance indicates whether a record came from imported decoded data, a native path, or another source. Keep that context when exporting or comparing results.
- Confidence and warning fields describe parser/source certainty; they are not regulatory or safety determinations.
- Remote ID observed radio MAC, UAS ID, serial/session ID, and operator ID have different meanings. Do not treat a MAC as permanent aircraft identity or infer commercial use from identifiers.
- Remote ID altitude references and units matter. Geodetic altitude and height above ground are shown separately in meters and must not be confused with the shared aircraft altitude field in feet.
- Authentication status from an upstream receiver is source-reported metadata. AeroHub does not independently verify it merely because the record passed JSON/schema validation.
- Consider operator identifiers, coordinates, raw payloads, and export files sensitive operational data. Store and share them only as permitted by your local policy and applicable regulations.
